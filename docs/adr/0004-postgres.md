# ADR-4 (amended): Postgres backend alongside SQLite

- **Status:** Accepted. Original decision 2026-10-15 ("SQLite default, Postgres later"); amended 2026-10-17: the Postgres port is ordered by the owner and executes as iteration 4. Implemented 2026-10-17 (iteration 4): Postgres ships as a beta backend; decision 6 is the copy tool in `apps/server/src/cli/copyToPostgres.ts` (runbook in docs/install.md section 15). Decision 5 deviates as recorded in the plan (application-side tokenizing, no generated column, no `ts_headline`).
- **Deciders:** the owner (owner), recorded by the iteration 3 Task 18 implementer.
- **Plan:** `docs/superpowers/plans/2026-10-18-iteration-4-postgres.md`

## Context

ADR-4 shipped SQLite (better-sqlite3 + Drizzle, WAL) as the only engine and named Postgres as the M5 escape hatch for the risk "SQLite write contention as data grows" (design.md risk table). Iteration 3 Task 18 was briefed as a gated assessment: port only if a mechanical path of about two agent-days with zero SQLite regressions existed. The inventory below shows it does not: the codebase is synchronous end to end, and several security and queue guarantees rest on that synchronicity. On 2026-10-17 the owner ordered the port regardless, so the gate is moot and this record captures the decision, the evidence, and the chosen strategy.

## Decision

1. Opportun gains a Postgres 16 backend selected by `DB_DIALECT=postgres` + `DATABASE_URL`. **SQLite stays the default and fully supported**; every server test runs against both engines in CI.
2. The port goes **async-first on SQLite**: before any Postgres code lands, the data layer becomes async (Drizzle's async `sqlite-proxy` driver over better-sqlite3, behind an in-process write gate), so the inversion of the sync-transaction assumptions is proven against the existing 949-test suite with the engine unchanged.
3. Check-then-act sequences that are only safe because transactions are synchronous are rewritten into **dialect-neutral atomic forms** (compare-and-set `UPDATE ... WHERE ... RETURNING`, unique indexes + `ON CONFLICT`, a per-user scope lock) while still on SQLite, each with a racing test.
4. Postgres schema history starts from a **baseline migration generated at cutover** (the SQLite chain's head, seed rows included), then the two chains move in lockstep with a CI parity check. Replaying the 19 historical SQLite migrations in a second dialect is rejected: no Postgres install exists to upgrade, and the history is mostly prompt-text rewrites.
5. FTS5 is replaced on Postgres by a `tsvector` design (generated column + GIN, `ts_headline` snippets) with a search-parity suite; SQLite keeps FTS5.
6. Existing installs (the owner's live data) move with a verified `sqlite -> postgres` copy tool; there is no automatic cutover.

## Strategy details

- **Async on SQLite first.** `drizzle-orm/sqlite-proxy` (already in the installed `drizzle-orm@0.45.4`, async `transaction` with `begin`/`commit`/savepoints) executes through one callback we own. That callback runs better-sqlite3 statements and enforces a process-wide **write gate**: while a transaction holds the gate (identified via `AsyncLocalStorage`), every statement from any other async context waits. This reproduces today's "nothing interleaves with a transaction" guarantee. Without the gate, another request's statement would run on the shared connection _inside_ the open transaction and commit or roll back with it.
- **No external I/O inside transactions.** Today it is impossible (bodies are sync); after the inversion it becomes possible and would stall every request behind the gate. Enforced by a slow-transaction warning in tests and by review.
- **Dialect-neutral hotspots** are fixed on SQLite first, so the semantics change is tested against the known-good engine before Postgres exists.
- **One seam.** `apps/server/src/db/client.ts` owns the driver, PRAGMAs, migrator, dialect-bound types (`Db`, `Exec`, `DbTable`, `DbColumn`), the health ping, close, and driver error mapping. Landed in iteration 3 (`92d27f6`) with no behavior change.

## What stays true

- SQLite remains the default for every install; nothing changes for a user who never sets `DB_DIALECT`.
- Single-process design: one Fastify process with its in-process job runner. Postgres does not imply horizontal scaling; a second process is out of scope (the claim query is nonetheless made multi-worker safe).
- WAL, short transactions, `busy_timeout`, and the locked migrator keep SQLite healthy at realistic volumes. A single job seeker produces on the order of 10^3-10^5 rows per year (opportunities, communications, activities), far below SQLite contention limits. The port is a capability and operations choice (managed databases, external backups, tooling), not a response to measured contention.
- `DATA_DIR` remains required under Postgres: attachments, backups, exports and `master.key` live on disk. Vault ciphertexts are copied byte-for-byte; the master key does not change.

## Consequences

- Positive: managed-Postgres deployments, standard backup tooling, a path to multi-process later; the async data layer removes the event-loop blocking of large synchronous queries.
- Negative: two dialects to maintain (schema twin, lockstep migrations, a few dialect SQL helpers, two search implementations); CI time roughly doubles for the server suite; a new runtime dependency (`pg`) needs a ledger ruling; the write gate serializes SQLite reads behind an open transaction (acceptable at these volumes, revisitable with a read connection).
